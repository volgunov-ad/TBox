# Пользовательские автоматизации

Автоматизация — сохранённое правило:

```
один или несколько триггеров (ИЛИ)
    → общие условия (И)
    → последовательность действий
```

Движок работает внутри `BackgroundService`. Открытый UI для выполнения не требуется.
Одно правило не стартует чаще чем раз в 2 с; после 5 ошибок подряд оно выключается до
ручного включения.

## Меню и хранение

- Пункт левого меню **«Автоматизации» по умолчанию скрыт**.
- Его можно включить и переставить в «Настройки → Левое меню».
- Скрытие пункта меню не выключает сохранённые правила.
- Определения хранятся версированным JSON в `settingsDataStore`
  (`vad.dashing.tbox.automations_json`) и автоматически входят в полный backup настроек.
- Одно невалидное правило (например, стекло **5 %** после смены allowlist) **не блокирует**
  остальные: его выключают, в карточке показывают ошибку, его можно открыть и исправить.
  Весь список прячется только при битом JSON / чужой `formatVersion` / повторе id.
- Автоматизации не являются частью `.tboxtheme` и не меняются при активации темы.

Экран содержит список правил, индивидуальные переключатели, создание, редактирование,
дублирование, удаление, **«Экспорт JSON»** (одна автоматизация в Загрузки, тот же
`formatVersion` / `automations[]`) и **«Выполнить сейчас»**. В шапке — **«Импорт»**
файла: документ, одиночное правило или массив. Совпадающие id получают новый uuid,
остальные поля как в файле. Кнопка «Выполнить сейчас» сразу запускает сохранённые
действия (без проверки триггера и общих условий); блоки `Если` внутри действий
считаются как обычно. Выключенное правило тоже можно прогнать. Действуют пауза 2 с
и глобальный ограничитель частоты; ошибки ручного запуска правило не отключают.
Дубль получает новый id правила, имя с суффиксом « (копия)»,
выключен и вставляется сразу после исходного; ID триггеров копируются как есть.
В редакторе триггеры и действия можно менять местами. Сначала сохраните черновик —
иначе кнопка в редакторе недоступна.

ID триггеров уникальны **только внутри одного правила**. По умолчанию они нумеруются
`1`, `2`, `3`… (можно править вручную). В разных автоматизациях можно использовать
одни и те же ID: условие «Сработал триггер» смотрит только на триггеры своего правила.

## Триггеры

Несколько триггеров одного правила всегда объединяются через **ИЛИ**. Если в одном цикле
совпали несколько, используется первый реально сработавший триггер; при равенстве —
первый по порядку в правиле. Его ID попадает в контекст `TriggeredBy`.

### Обязательные системные события

| Событие | Когда формируется |
|---------|-------------------|
| **Фоновая служба полностью запущена** | `BackgroundService` завершил startup pipeline и перешёл в `ServiceLifecyclePhase.Running` |
| **Открыт главный экран программы** | `MainActivity` стал foreground на `main_screen` либо был открыт MainScreen-overlay оконного режима |
| **Открыто меню программы** | `MainActivity` стал foreground на любой вкладке левого меню или выполнен переход с главного экрана в консоль |

Compose-рекомпозиции не считаются повторным открытием. Переход между вкладками уже открытого
меню также не создаёт новое событие «Открыто меню».

### Сигналы TBox и ГУ

Источник выбирается явно для каждого триггера и условия:

- **TBox**;
- **mbCAN/VHAL** (текущий backend ГУ).

Автоматического fallback между TBox и ГУ нет. UI показывает только источники, для которых
сигнал поддерживается. Списки сигналов, действий и CAN-команд в настройках отсортированы
по подписи. После выбора сигнала в триггере или условии показывается подсказка
с возможными значениями: состояния (`P/R/N/D`, on/off, режимы сидений), именованные режимы
(`ECO`, `AUTO`, `LDW` и т.п.) или типичный диапазон.

**Режим движения** (`drive_mode`) и **режим фар** (`headlight_mode`) — состояния с именованными
значениями (`ECO`/`NOR`/`SPT`, `AUTO`/`PARK`/`LOW`/`OFF`), не raw-коды ГУ. При импорте старых
JSON числовые условия и `expectedState` `"2"`/`"4"` для этих сигналов автоматически
преобразуются в строки на decode.

Числовой триггер задаёт:

- направление: «стало больше» или «стало меньше»;
- основной порог;
- порог повторного взведения (гистерезис) — **по умолчанию включён**, можно выключить;
- настраиваемую непрерывную выдержку «в течение» N секунд (`0` — сработать сразу после пересечения).

Например: `RPM > 1000`, в течение `2 с`, повторно взвести при `RPM <= 900`.
Сигнал должен **пересечь** основной порог (для «стало больше» — стать строго больше), затем
непрерывно оставаться выполненным N секунд. Краткий обрыв сигнала сбрасывает таймер выдержки,
но не разряжает триггер: при возврате значения выдержка начинается заново.
Порог повторного взведения — это линия, которую нужно **достичь или пересечь** в обратную
сторону (`<=` для «стало больше», `>=` для «стало меньше»). Точное равенство порогу не требуется:
скачок `1500 → 900` при пороге взведения `1000` взводит триггер снова.

Если порог повторного взведения **выключен**, гистерезиса нет: правило срабатывает на каждое
**новое** число, пока условие порога ещё истинно (например температура 9.5 → 9.0 → 8.2 при
«стало меньше 10»). Повтор той же цифры с шины не считается событием. Мелкая дрожь датчика
даст частые запуски. Старые JSON без поля `rearmEnabled` ведут себя как включённый порог.

Для состояний (`P/R/N/D`, AccStatus, on/off, режим сиденья и т.п.) доступна такая же выдержка.

Состояния **ESP-реле 0–1** и **ESP-входов 0–3** берутся с USB-компаньона (источник
«Приложение»). Пока компаньон не подключён, сигнал недоступен — как обрыв TBox/ГУ.

**Педаль газа** (`gas_pedal`) и **педаль тормоза** (`brake_pedal`) — только ГУ (mbCAN/VHAL).
Газ — число 0…100 % (невалидный EMS-флаг или вне диапазона → нет значения). Тормоз —
состояние `on`/`off` по `BrakePedalSts`: **2** = нажата, **1** = отпущена (0 и прочие → нет значения).
Те же сигналы, что у виджета «Газ/тормоз»;
TBox UDP `breakingForce` сюда не входит.

**Режим дворников** (`wiper_sts`) — только ГУ. Состояния `off` / `int` / `low` / `high`
(TTG 0/1/2/3). Raw **1** всегда INT, даже если на части комплектаций штатная иконка AUTO.
Это не сервисное положение (`wiper_maintenance`). Тот же live `WiperSts`, что на иконке
виджета обслуживания дворников.

**Детектор дождя** (`rain_detected`) — только ГУ. Состояния `on`/`off` по CEM 1-bit
(`getRainDetectedSts` / `R_0400_CEM_2_RainDetected` **289412139**): **1** = дождь
(`S_RAIN` TRUE в электросхеме), **0** = сухо. Штатный CarSettings этот бит не рисует.
Это не отказ датчика (`RainSensorFailSts` **289412141**) и не режим дворников.

**Шторка** (`sunshade`) — только ГУ. Состояния `closed` / `open` (0/1 закрыто, 2…11 и 10…100
открыто). На A9 live идёт через `canGet` / cfg **46** (в BCM поля шторки нет). На A10 — `Abat_VentCMDSts`.

**Люк** (`sunroof`) — только ГУ. Состояния `closed` / `open` / `tilt`.
Запись по-прежнему **1…11** и **12** (откинуть). Статус на A9 — другая шкала:
**0** закрыто, **10…100** открыто, **102** откинут (команда **12** тоже tilt).
Live только `canGet` / cfg **45**, не BCM `getSunRoof` (там постоянно −1). A10: `PSRFCMDSts`.

**Стёкла** (`window_front_left` / `window_front_right` / `window_rear_left` /
`window_rear_right`) — только ГУ, по одному стеклу. Состояния `closed` / `open` / `vent`.
Положение 0…100 %: **0** закрыто, **1…30** щель (штатная щель 20), **31…100** открыто.
Команды A9 только **0 / 20 / 80 / 100**.
A9: BCM `getVehicleWindow`. A10: `*_WIN_Position` (процент, не команда записи 1/2/3).

**Приложение на экране** (`foreground_app`) — только источник «Приложение». Состояние —
имя пакета (тот же список, что у запуска приложения). Нужен доступ к статистике
использования. Общий опрос с правилами плавающих панелей: **1 с**, окно `queryEvents`
**10 с**; пустой тик держит последний пакет. Пакет самого TBox считается передним планом,
только если открыт главный экран — в том числе когда UsageStats пустой (на ГУ часто нет
события своей Activity). Иначе после добавления первого правила первым значением может
стать AVM, и оно запомнится как база без запуска. Без разрешения UsageStats сигнал всё
равно публикует TBox при открытом главном экране и AVM через `avm_state`. Несколько приложений —
несколько OR-триггеров, не мультивыбор. У панелей поверх этого есть debounce из двух
опросов; автоматизации его не используют (выдержка «в течение» и поведение при старте).

Камера 360 **`com.mengbo.avm`** не остаётся resumed Activity: картинка — оверлей службы.
Для неё тот же триггер смотрит штатный `Settings.Global avm_state` (и `SHOW_AVM_EVENT`),
а не UsageStats. Новый тип триггера не нужен — в правиле по-прежнему выбирается пакет AVM.

### Геопозиция

Триггер **геозоны** использует текущую точку из `GeoDisplayRepository`: выбранный GNSS-источник,
а если включена подмена — ту точку, которую программа пишет в систему.

Пользователь вставляет координаты текстом (тот же разбор, что «Вставить координаты» на карте:
Яндекс / Google / 2GIS / `geo:` / десятичные пары / DMS). Сохраняются и исходная строка, и
разобранные lat/lon.

Два радиуса вокруг точки, направление **вошёл** или **выехал**, выдержка «в течение»:

- **Вошёл:** срабатывание при дистанции **≤ радиуса зоны**; повторное взведение после
  дистанции **> радиуса взведения** (второй радиус больше первого).
- **Выехал:** срабатывание при дистанции **> радиуса зоны**; повторное взведение после
  дистанции **≤ радиуса взведения** (второй радиус меньше первого).

Кольцо между кругами — серая зона: ни новый запуск, ни взведение. Если за время выдержки
условие нарушилось, таймер сбрасывается, триггер остаётся взведённым.

При изменении радиуса зоны второй радиус подставляется автоматически (**+10 м** для входа,
**−10 м** для выхода, не ниже 0), **только если** он уже не находится с нужной стороны от
первого.

Нет фикса / потеря точки — как `Unavailable`: выдержка сбрасывается, боевой взвод не
теряется. Включение и правка правила, если уже внутри/снаружи зоны, только формируют базу.

### Время

Триггер **«Время»** срабатывает один раз, когда местные часы ГУ входят в указанную минуту
(`ЧЧ:ММ`). Дни недели необязательны: ничего не отмечено — каждый день. Часовой пояс —
системный ГУ. Если фоновая служба в эту минуту не работала, момент **не догоняется**, пока
выбрано «Запомнить начальное состояние».
Для ожидания условий триггер считается уже выполненным, как системное событие.

У триггера **«Время»** есть **«Если условие выполнено после перезапуска службы»**:

- **Запомнить начальное** — как раньше, момент не догоняем.
- **Запустить автоматизацию** — если служба поднялась **в этот день после назначенной
  минуты** (и день недели подходит), правило **один раз догоняет**. «07:30» и старт в
  10:00 → запуск. Вчерашний момент после полуночи не догоняем. Включение и правка
  правила по-прежнему только база, без запуска.

Условие **«Время»** проверяет текущие часы ГУ:

- **после** (включительно) и/или **до** (не включая эту минуту);
- дни недели; ничего не отмечено — любой день;
- если «после» позже «до», окно идёт через полночь (`22:00`–`06:00` = ночь);
- если «после» и «до» совпадают, условие истинно только в эту минуту;
- нужно задать хотя бы окно или дни недели.

Календарные даты и «каждые N минут» в этот срез не входят.

### Восход и закат

Триггер и условие **«Восход / закат»** считают официальный диск солнца (зенит 90.833°),
не гражданские сумерки. Точка — **текущая или последняя** из `GeoDisplayRepository`
(GNSS или подмена). Нет точки или в этот день нет события (полярный день/ночь) —
триггер не срабатывает, условие ложно.

Смещение **0…180 мин**, **до** или **после** события. Дни недели как у «Время».
Часы и пояс — системные ГУ. В редакторе, если есть точка, показывается сегодняшнее ЧЧ:ММ.

Триггер срабатывает в ту минуту, когда наступает рассчитанный момент (если смещение
ушло на следующие сутки, то уже в эти сутки). Та же опция после перезапуска службы,
что у «Время»: «Запустить автоматизацию» догоняет, если **сегодняшний** восход/закат
со смещением уже позади. Пример: «закат + 2 ч», старт через 3 ч после заката → запуск.
Координаты пришли на минуту позже старта службы — догон тогда же, как первое число у RPM.

Условие — два края **после** / **до** (каждое: восход или закат ± смещение). Через полночь
как у «Время» («после заката» + «до восхода» = ночь).

### Инициализация

Для каждого signal-триггера настраивается поведение после перезапуска службы, если первое
валидное значение уже удовлетворяет условию:

1. **Запомнить начальное состояние** — без запуска (по умолчанию). Текущее значение
   становится базой; правило сработает только после повторного взведения и нового
   выполнения условия.
2. **Запустить автоматизацию** — правило запускается сразу (с соблюдением настроенной
   выдержки «в течение»). После этого триггер разряжается до повторного взведения.

Включение или редактирование правила всегда только формирует начальное состояние, независимо
от этой настройки. После стартового запуска триггер остаётся разряженным до достижения порога
повторного взведения.

## Условия

Поддерживаются:

- числовые сравнения `>`, `<`, `>=`, `<=`, `=`, `!=`;
- сравнение состояния (`P/R/N/D`, on/off, режимы сидений `heat_1`…`vent_3`, режимы фар, drive mode и др.);
- **геозона** — внутри/снаружи точки с радиусом (та же модель координат, что у триггера геозоны; без повторного взведения);
- **состояние приложения** — фоновая служба запущена, открыт главный экран, открыто меню;
- окно времени и дни недели (часы ГУ, в том числе через полночь);
- окно восход/закат (нужна текущая или последняя геопозиция);
- проверка ID сработавшего триггера — можно отметить несколько ID;
- группы `И`, `ИЛИ`, `НЕ`.

Помимо базовых телеметрий TBox/ГУ, в условия и триггеры доступны **CAN-параметры** из
безопасного каталога (замки/свет, ADAS без AEB, климат, HUD, аудио A9 и т.д.) — см. те же
подписи, что у CAN-действий (`AutomationParameterLabels`). Исключены сомнительные/нечитаемые
пункты: AEB, safe distance, wireless charge, pulse складывания зеркал, все стёкла разом,
PM2.5, UV, sterilize, brake feel, car wash, system mode, power mode, source station.

Условия верхнего уровня объединяются через `И`. Один параметр **«Ждать условие, с»**
относится ко всей этой группе, не к каждому условию отдельно: `0` — если на момент
триггера группа ложна, запуск сразу пропускается; `> 0` — ждать до таймаута, пока
**одновременно** истинны сработавший триггер (повторная проверка текущего значения;
системное событие и триггер «Время» считаются уже выполненными) и все условия. Если во время ожидания
триггер временно перестаёт выполняться, окно **не отменяется** — успех возможен, когда
оба снова истинны до истечения времени. По истечении таймаута без такого момента
действия не запускаются.

Условие внутри действия `Если` вычисляется
в момент достижения этого действия, то есть после предыдущих задержек.

## Действия

Действия выполняются последовательно. Если исходное условие триггера позже перестало
выполняться, уже начатая последовательность **продолжается**.

Поддерживаются:

- все CAN-настройки из безопасного каталога; значения в списке подписаны
  (подогрев/вентиляция сидений, режимы фар, температура в °C, шторка/люк/стёкла и т.п.),
  а не сырыми кодами. Шторка **1…11** (закрыто…открыто), люк **1…11** и **12** (откинуть)
  одинаково на A9 и A10. Стёкла: A9 **0 / 20 / 80 / 100** (машина не держит промежуточные), A10 **1** закрыть / **2** открыть / **3** щель;
- действия TBox Monitor (поездка, моточасы, тема, **плавающие панели — видимость/включение**
  для всех панелей или одной выбранной: переключить / скрыть / показать и
  переключить / включить / выключить, ESP-реле, mock location, geo log);
- медиакоманды и громкость (виджет музыки не нужен; Play / Play-Pause при отсутствии
  MediaSession запускают выбранный плеер и шлют play, как виджет, но **без возврата**
  в TBox Monitor; нужен доступ к уведомлениям, как у виджета);
- запуск приложения fullscreen, freeform или в штатном Adayo-окне;
- выбор стороны/размера freeform, crop и страницы соседнего MainScreen;
- открытие конкретной страницы MainScreen fullscreen или в текущем freeform-overlay;
- HTTP-запрос либо открытие URL;
- Toast с произвольным текстом;
- сообщение на экране с текстом и кнопкой «Закрыть» (ждёт закрытия или автозакрытия через N секунд при N>0; на окне показывается обратный отсчёт; нужно разрешение «Поверх других окон» из «Настройки → Разрешения», само по себе не выдаётся);
- настраиваемая задержка;
- рекурсивное `Если → То → Иначе`.

Режимы повторного запуска: `single`, `restart`, `queued`, `parallel`.

### Плавающие панели: видимость и включение

Два разных механизма:

| Действие | Что меняется | После перезапуска приложения / службы |
|----------|--------------|----------------------------------------|
| **Видимость** (скрыть / показать / переключить) | Временный список скрытых панелей в памяти службы | Не сохраняется. Панели снова могут появиться, если в настройках включено **«Показывать плавающую панель»** и нет других ограничений (правила скрытия по приложениям, разрешение «Поверх других окон»). |
| **Включение** (включить / выключить / переключить) | Переключатель **«Показывать плавающую панель»** в настройках каждой панели | Сохраняется. Состояние остаётся после перезагрузки. |

Чтобы панель **не появлялась и после перезагрузки**, используйте **выключение**, а не только **скрытие**.

При **включении/выключении** временное скрытие всех панелей сбрасывается (как после плитки «отключение плавающих панелей»).

## CAN-безопасность

Пользователь не вводит raw property ID. `AutomationCanCatalog` строится поверх
`MbCanCommandRegistry` / `MbCanAudioCommandRegistry` и проверяется повторно при загрузке JSON.

Не публикуются:

- политики `SetAnyInt`;
- reboot ГУ;
- MFS/ACC/CCS cruise pulses;
- raw speed-limiter probes.

Электропривод багажника доступен только как штатный pulse (`TrunkPulse` 1/2), как у виджета
на главном экране: отдельной программной проверки скорости или PRND нет. Ограничения
движения, если они есть, остаются на стороне автомобиля.

Шторка (**46**) и люк (**45**) пишутся через `canSetVehicleParam` / VHAL с теми же сырыми
значениями на обеих ГУ. Стёкла на A9 идут через `canSetWindowStatus` (не property 47/55–58);
на A10 — четыре `WindowCon_Req`. Список значений в редакторе зависит от текущего backend ГУ.

Все записи выполняются только через `UniversalCanRepository`, поэтому сохраняются backend
mapping, ограничения значений, JNI-сериализация, post-command refresh и диагностика.

## Перезапуск и отмена

- При выключении, удалении или редактировании правила его текущие job и очередь отменяются.
- Незавершённые задержки не восстанавливаются после перезапуска процесса/службы.
- `null`, `Unknown` и `Unavailable` не удовлетворяют триггеру или условию.
- Ошибка действия останавливает текущую последовательность и сохраняется в runtime-статусе
  списка и журнале с тегом `Automation`.
- Повторный запуск одного правила не чаще чем раз в 2 с (включая `restart`/`parallel`).
- После 5 ошибок подряд правило выключается и остаётся выключенным до ручного включения.
- Очередь событий движка ограничена (256); поставщики сигналов притормаживаются, а `StateFlow`
  телеметрии сам схлопывает промежуточные значения.
- mbCAN get/set идут через `UniversalCanRepository` → `MbCanRepository` на поток
  `mbcan-state-apply`, не с UI-потока. VHAL-записи автоматизаций выполняются на `Default`.
