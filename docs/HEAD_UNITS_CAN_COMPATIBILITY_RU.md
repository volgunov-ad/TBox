Дата исследования: 16.10.2026. Источники: локальные материалы `D:\Dashing`, чтение двух работающих ГУ по ADB, статический анализ MCU и штатных конфигураций. Перепрошивка, изменение конфигурации, перезагрузка и отправка команд управления автомобилем в ходе исследования не выполнялись.

Связанные документы: [профили ГУ](HEAD_UNITS_DEVICE_NOTES_RU.md), [mbCAN/VHAL](CAN_BACKENDS_RU.md), [формулы сырых значений](RAW_VALUE_FORMULAS_RU.md), [протокол TBox](TBOX_PROXY_RU.md).

## 1. Итог и границы вывода

**A9 и A10 используют существенно пересекающийся набор автомобильных CAN ID и сигналов. Различие Android API (mbCAN/VHAL) само по себе не препятствует замене ГУ целиком с родным MCU. Полная взаимозаменяемость конкретных экземпляров не доказана.**

Корпуса разъёмов одинаковые по сообщению владельца; электрическая распиновка, распределение физических CAN-каналов и скорости шин в исследовании не проверялись. Совпадение ID не доказывает совпадение всех битовых полей, кодировок, CRC, периодов и сетевого управления.

Особенно важно ограничение A9: на устройстве работает MCU117, а доступные ELF относятся к MCU097/101 и имеют в имени `JX65-Intel`. Их соответствие аппаратной ревизии живого Qualcomm X50 полностью не установлено. Нельзя описывать их CAN-таблицы как дамп работающего MCU117.

**Использовать результаты для расширения декодера TBox можно как источник гипотез и для восстановления точных карт сигналов, но не как готовую DBC для потока TBox.** Подробности и обнаруженные конфликты ID — в §7.

## 4. Архитектура обмена

```text
A9:  Android mbCAN → mb_can_service → собственный UART-протокол → MCU → CAN автомобиля
A10: Android Car/VHAL → Adayo MCU-стек → UART ttyAT3 → MCU → CAN автомобиля
```

`VehicleConfig.json` A10 направляет INFO, HVAC, AVM, CLUSTER, BCM, TBOX и другие группы через `datacomm: MCU`.

В живом журнале A10 наблюдались UART-кадры с префиксом `6A A6`, служебные сообщения `8305`, `8B30`, `8401`, heartbeat и подтверждения. Это внутренний транспорт SoC↔MCU, **не сырые CAN-кадры**. Внутренние протоколы A9 и A10 не взаимозаменяемы.

`FuncID/cmdID` JSON, например `02/01` или `04/01`, и числа VHAL property **не являются автомобильными CAN ID**. Префикс `T_0401_` в имени property не означает CAN ID `0x401`.

### 5.3. Проверенные примеры полей и совпадения имён

Нумерация байтов и битов ниже — с нуля, бит 0 — младший.

- A9 MCU101 `IlPutTxIHU_1_DVD_SET_AutoLockSts` по адресу `0x54E3C`: запись 2 бит в байт 1 буфера `IHU_1` (`0x515`). A10 property `T_0401_IHU_1_DVD_SET_AutoLockSts=289412661` находится в UART mByte=4, start=0, len=2; MCU A10 переносит соответствующий байт команды в байт 1 `IHU_1`. Здесь прослежено совпадение конкретного поля.
- A9 MCU101 `IlPutTxIHU_5_BlowSpeedLevel_Req` по адресу `0x53AFC`: байт 0, биты 4…7 `IHU_5` (`0x52F`). A10 property `T_0201_IHU_5_BlowSpeedLevel_Req=289415296`, UART mByte=3, start=4, len=4; MCU A10 копирует первый байт команды в байт 0 `IHU_5`. Здесь также прослежено совпадение поля.
- Температуру нельзя объявлять полностью совпавшей: A9 `IlPutTxIHU_5_L_Set_Temperature` (`0x53E6C`) использует 7 бит в байте 5, начиная с бита 1; живой JSON A10 задаёт для левой температуры UART len=6 и другое размещение до переупаковки MCU. Масштаб и валидность требуют отдельной проверки.
- Сопоставление имён `IlPutTx*` MCU101 с `T_XXXX_*` в `VehiclePropertyIds.java` дало **122 точных текстовых совпадения** из 194 setters A9 и 222 T-property справочника A10. Это совпадения имён, не 122 доказанно идентичных декодера.

## 6. Что требуется для подтверждения взаимозаменяемости

1. Сверить электрическую распиновку, питание, CAN H/L, количество и скорость физических шин для обеих ревизий.
2. Получить точную карту установленного MCU117 или пассивные трассы этого ГУ; не подменять их MCU097/101.
3. Сравнить на одной машине поочерёдно установленными ГУ CAN ID, реальные DLC, payload, периоды, счётчики/CRC и ответы на штатные действия.
4. Проверить конфигурацию комплектации и двигателя/КПП. A10 использует собственные ключи `HMA214A_byteN_07` через SystemService; значения A9 не переносить как есть.
5. Проверить VIN/адаптацию, камеры, дисплей, усилитель, кнопки руля и приборную панель. Наличие VIN в настройках не доказывает наличие блокировки замены.
6. Проверить пробуждение, ACC OFF, закрытие и полноценный сон, ошибки блоков и ток покоя. Общий `NWM_IHU=0x618` не доказывает одинаковую политику сна.

Перепрошивать MCU A9 образом A10 или наоборот не требуется для проверки замены ГУ целиком; совместимость таких образов не установлена.

## 7. Применимость к декодеру сырых кадров TBox Monitor

### 7.1. Что уже делает программа

`app/src/main/java/vad/dashing/tbox/utils/CanFramesProcess.kt` обрабатывает записи CRT по 17 байт после удаления первых 4 байт ответа: CAN ID в записи с offset 4, payload с offset 9, 8 байт. Диспетчеризация идёт **только по CAN ID**; метаданные начала записи и байт перед payload не используются для выбора профиля/шины.

Декодер и экспорт в `tools/can_log_to_xlsx.py` отражают наблюдаемый поток TBox. Их существующие формулы нельзя заменять картой MCU ГУ только из-за одинакового ID.

### 7.2. Конкретные расхождения, обнаруженные при сопоставлении

| ID | Текущий декодер TBox | Название/роль в эталонной карте MCU ГУ |
|---|---|---|
| `0x430` | Скорость, напряжение, топливо, одометр | `CGW_BMS_24` |
| `0x51B` | Давление/температура шин | `CGW_FCM_2` |
| `0x535` | Температура салона и снаружи | `BMS_10` |
| `0x53A` | Качество воздуха | `MFS_3` |
| `0x52F` | Климатическая уставка, b5/4 | `IHU_5`, исходящие команды климата; не подтверждённый статус |

Это **не доказательство ошибки существующего декодера**: возможны разные физические сегменты, преобразования шлюза/CRT, конфигурации машины и семейства прошивок. Также остаётся ограничение происхождения ELF A9. Причина расхождений в этом исследовании не установлена.

Следствия:

- Не переименовывать TPMS `0x51B` в FCM и не декодировать биты ADAS по нему без проверки источника.
- Чтение кадра команды IHU показывает запрос пользователя, не обязательно фактическое исполненное состояние блока. Для статуса предпочтительны подтверждённые RX-сигналы соответствующего блока.
- JSON `receive.json/send.json` описывает поля **внутреннего пакета SoC↔MCU**, нередко длиннее 8 байт. Например, mByte=63 не является байтом CAN-кадра. MCU сначала агрегирует/переупаковывает автомобильные данные.
- VHAL scale тоже может относиться к уже преобразованному значению, а не к сырым битам CAN; пример разных масштабов RPM приведён в [RAW_VALUE_FORMULAS_RU.md](RAW_VALUE_FORMULAS_RU.md).

### 7.3. Что можно извлечь из материалов

- Имена сигналов и принадлежность к блокам: двери/замки/стёкла/люк, HVAC, сиденья, свет, радары, ADAS, кнопки руля — кандидаты, не обещание доступности всех данных через TBox.
- Точные byte/bit layout из `IlPutTx*`, DWARF-структур и кода MCU; отдельно от коэффициентов и enum, которые могут находиться в Android-доменах или преобразованиях MCU.
- Счётчики, флаги валидности, таймауты и checksum: позволяют отличать реальные изменения от служебных битов.
- Словарь имён для офлайн-анализа; подписи MCU должны содержать профиль источника и уровень уверенности.

**В этом изменении новые боевые декодеры не добавлены.** Исследование дало таблицы ID и несколько полей, а не полную подтверждённую карту TBox.

### 7.4. Рекомендуемый порядок расширения

1. Сохранить исходные записи CRT и проверить смысл метаданных: есть ли номер CAN-канала/признак источника. Не назначать поле шины по догадке. Если нескольких источников различить нельзя, конфликтующие карты не включать одновременно.
2. Восстановить для одного RX-сигнала полную цепочку: CAN ID + канал/профиль → байты и биты MCU → агрегация UART → property → физическая величина/enum, invalid и timeout.
3. Проверить наличие соответствующего кадра именно в TBox-экспорте. Декодер не может создать сигнал, который CRT не передаёт; расширение списка выдачи — отдельное исследование протокола.
4. Сопоставить пассивный TBox-лог с подтверждённым mbCAN/VHAL-статусом и метками обычных штатных действий на неподвижной машине. Пустые/неизменные значения на стенде не доказывают семантику сигнала.
5. Сначала проверить декодирование офлайн, включая несовпадающий профиль, invalid, endian, границы и timeout. Рекомендуемая первая группа — дискретные кузовные статусы при подтверждённых кадрах, не замена скорости/топлива/RPM.
