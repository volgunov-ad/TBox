# План: источники курса (CAN, телефон, компас) и геопозиция с телефона

Курс нужен улучшенной геопозиции (`MockLocationJob`, режимы `MockCanSpeedMode`): без GNSS машина ведётся счислением по скорости CAN и курсу. Сейчас курс берётся из гироскопа ГУ, руля или их гибрида (`MockHeadingSource`: `GYRO`, `STEER`, `GYRO_STEER`). Этот план добавляет курс по CAN-колёсам, гироскоп и компас телефона и геопозицию с телефона.

Связанные документы: [WHEEL_PULSE_ODOMETER_RU.md](WHEEL_PULSE_ODOMETER_RU.md), [PHONE_COMPANION_BLE_PLAN_RU.md](PHONE_COMPANION_BLE_PLAN_RU.md) §8, [MBCAN_VHAL_PARAMETERS_RU.md](MBCAN_VHAL_PARAMETERS_RU.md), [reference/vhal_properties_a10_2026-10-21.csv](reference/vhal_properties_a10_2026-10-21.csv).

---

## 1. Почему: на A10 нет гироскопа

Проверено на ГУ A10 (192.168.1.7, 21.10.2026). Ни один из трёх путей гироскопа не даёт данных.

| Путь | Что в коде | Что на ГУ |
|------|------------|-----------|
| Navi DR Adayo | `A10NaviDrBackend`, binder `adayo.service.navi.v2.0` | Сервиса и пакета навигации Adayo нет: `binder null`. |
| Android `SensorManager` | `AndroidSensorDrBackend` (запасной) | HAL `sensors.ac8x.so` объявляет ASM330LHH (акселерометр + гироскоп), но драйвера в ядре нет: нет input-устройства «ST ASM330LHH Gyroscope Sensor», на шинах I²C датчика нет. Подписка приложения кончается `SensorService: Error activating sensor 4 (Operation not permitted)`. |
| INS от MCU через VHAL | не используется | Свойства `MPU_ASK_INS_DATA_INFO` (0x21400CC7), `MCU_SEND_INS_ANGULAR_VELOCITY` / `_ACCELERATION` / `_TEMPERATURE` / `_SPEED` (0x21400CC8…CB) есть, но нулевые, `timestamp 0`. Запрос `MPU_ASK_INS_DATA_INFO=1` к MCU по UART не уходит, ответа нет. |

Магнитометра на ГУ нет ни на A9, ни на A10.

## 2. Источники

### 2.1 CAN (A9 и A10)

| Сигнал | A9 (mbCAN) | A10 (VHAL) | Для курса |
|--------|------------|------------|-----------|
| Импульсы колёс LHF / RHF / LHR / RHR | `eMBCAN_VEHICLE_WHEEL` → `MBCanVehicleWheel` | `R_0400_ESP_5_*PulseCounter`: 289412182 / 289412179 / 289412175 / 289412177 | Поворот = (ΔsR − ΔsL) / колея, по задним колёсам |
| Поперечное ускорение | `MBCanVehicleSpeed.fLateraAccaleleration` | `R_0900_YAS_1_LateraAccaleleration` (289414960) | ω ≈ a_lat / v, только для подтверждения |
| Угол руля | уже есть (`STEER`) | уже есть (`MCU_REPLY_STEERING_WHEEL_ANGLE`, `SteeringAngleDomain`) | Модель велосипеда, `SteerHeadingIntegrator` |
| Скорости колёс `0x310` | через TBox (`CanFramesProcess`) | через TBox | Запасной дифференциал колёс, только при связи с TBox |

Готового сигнала угловой скорости рыскания (yaw rate) нет ни на A9, ни на A10.

### 2.2 Телефон (только Android)

| Данные | Откуда в телефоне | Зачем |
|--------|-------------------|-------|
| Координаты, скорость, курс по движению, точность, число спутников | Сырой `LocationManager.GPS_PROVIDER` + `GnssStatus` (не `FusedLocationProvider`, чтобы избежать двойного map-matching и удержания точки от Google Play Services) | Новый источник геопозиции |
| Угловая скорость вокруг вертикали | `TYPE_GYROSCOPE`, проекция на гравитацию (`TYPE_GRAVITY` / акселерометр) | Курс как от гироскопа, при любой ориентации телефона |
| Азимут по компасу | `TYPE_MAGNETIC_FIELD` + гравитация, без `TYPE_ROTATION_VECTOR` (внутри у него смешан гироскоп) | Абсолютный курс, в том числе на стоянке |
| Модуль поля, точность магнитометра | `onAccuracyChanged`, |B| | Отбраковка компаса |

## 3. Варианты выбора источника курса

`MockHeadingSource` расширяется. Выбор один на оба ГУ; недоступные на этом ГУ варианты видны, но помечены «недоступно» с причиной.

| Вариант | Что делает | A9 | A10 |
|---------|------------|----|-----|
| `GYRO` | Гироскоп ГУ (`YawIntegrator`) | да | нет (см. §1) |
| `STEER` | Руль | да | да |
| `GYRO_STEER` | Гироскоп + руль (как сейчас) | да | нет |
| `WHEELS` | Дифференциал импульсов задних колёс | да | да* |
| `WHEELS_STEER` | Колёса основной, руль на малой скорости и для подтверждения | да | да* |
| `PHONE_GYRO` | Гироскоп телефона | да | да |
| `PHONE_COMPASS` | Компас телефона, абсолютный курс | да | да |
| `PHONE_GYRO_COMPASS` | Гироскоп телефона для поворотов + компас для медленной поправки абсолютного курса | да | да |

\* После проверки на A10 в движении, что импульсы приходят через VHAL с достаточной частотой (§7, этап 0).

Поперечное ускорение отдельным вариантом не выбирается: только вес подтверждения поворота в гибридах.

Если выбранный источник замолчал (нет данных дольше порога, телефон отключился, компас забракован), курс временно берётся из следующего доступного по цепочке: телефон → колёса → руль. Факт подмены виден в статусе и пишется в geo-debug.

## 4. Курс по CAN-колёсам

Новый `WheelHeadingIntegrator` рядом с `SteerHeadingIntegrator`.

- Вход: те же сэмплы импульсов, что у `WheelPulseOdometer` (одна подписка, без второго опроса mbCAN/VHAL; правила потоков mbCAN из [MBCAN_JNI_THREADING_RU.md](MBCAN_JNI_THREADING_RU.md)).
- Δψ = (ΔsRR − ΔsRL) / B, где Δs = импульсы × k (k из калибровки `WheelPulseOdometer`), B — эффективная колея (ведомая задняя ось, в отличие от ведущей передней для дистанции в `WheelPulseOdometer`).
- B калибруется автоматически по GNSS-курсу на дугах при движении вперёд (`!reverse`, как `SteerCalibrationStore` / `GyroBiasStore`), стартовое значение — паспортная колея.
- Переполнение счётчиков (13 бит, `0…8191`) и пропуски сэмплов — как в `WheelPulseOdometer`.
- Ограничение дискретности и выбросов: на малой скорости единичный импульс разницы `ΔsRR − ΔsRL` не должен давать ступеньку курса; импульсы накапливаются в скользящем окне шага DR, а максимальная расчётная угловая скорость $|\omega_{\text{wheels}}|$ сверху ограничивается физическим потолком велосипедной модели по текущему углу руля (`SteerHeadingIntegrator`).
- Пробуксовка: если асимметрия передних и задних пар расходится сильнее порога (slip gate из `WheelPulseOdometer` §4.3), сэмпл не учитывается, курс на это время из руля.
- Малая скорость: ниже порога (≈5 км/ч, уточнить по данным) дискретность импульсов даёт шум, в `WHEELS_STEER` вес переходит к рулю.
- Задний ход: знак Δψ по передаче (`considerReverse`).
- Поперечное ускорение: при v > ≈20 км/ч ω_lat = a_lat / v сравнивается с ω колёс; сильное расхождение снижает доверие к колёсам.

## 5. Телефон

### 5.1 Фоновая работа, энергопотребление и управление соединением

Сейчас приложение `:phone` держит связь, только пока открыт экран (`PhoneActivity` останавливает `PhoneLinkRouter` в `onDispose`). Нужно:

- Foreground service с постоянным уведомлением, типы `location` и `connectedDevice`; разрешения `FOREGROUND_SERVICE_LOCATION`, `FOREGROUND_SERVICE_CONNECTED_DEVICE` (Android 14+), `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION` (снять `maxSdkVersion="30"` в `phone/src/main/AndroidManifest.xml`, сохранив `neverForLocation` на `BLUETOOTH_SCAN`), `ACCESS_BACKGROUND_LOCATION`.
- Автозапуск при появлении ГУ: связь с ГУ через `CompanionDeviceManager`. Тогда система будит приложение по Bluetooth и разрешает старт foreground service из фона (Android 12+). На Android 14+ (API 34) тип службы `location` включается при старте из фона только если уже выдано `ACCESS_BACKGROUND_LOCATION` («Разрешить в любом режиме»); иначе служба стартует как `connectedDevice` (гироскоп/компас работают) и подсказывает выдать фоновую геолокацию.
- Владение `PhoneLinkRouter` переносится в службу; `PhoneActivity` подключается к состоянию службы и не рвёт сокет при сворачивании экрана.
- Взаимодействие с `PhonePath.AUTO` и блокировка в режиме `PhonePath.COMPANION`:
  - В режиме **«Компаньон» (BLE)** (`PhonePath.COMPANION`) переключатели «Отдавать геопозицию», «Отдавать гироскоп» и «Отдавать компас» в приложении `:phone` **заблокированы (`enabled = false`)**, фоновая служба `PhoneTelemetryService` и автозапуск не запускаются, а в карточке выводится явное пояснение, что передача возможна только при прямом подключении к Bluetooth ГУ («ГУ напрямую» или «Авто»).
  - В режиме **«Авто»** (`PhonePath.AUTO`), если телефон ещё не привязан напрямую к ГУ (`!directPaired`), выводится предупреждение о необходимости прямого сопряжения с Bluetooth ГУ; если включён хотя бы один тумблер телеметрии, `PhoneLinkRouter` удерживает прямой RFCOMM-канал (`PhoneDirectLink`), не отключая его даже при ответе от ESP32 по BLE (`PhoneRadio`).
- Активация GPS и сенсоров по потребности (экономия батареи и нагрева): `LocationManager` и `SensorManager` на телефоне запускаются **только при подтверждённом RFCOMM-соединении с ГУ** (`direct.confirmed == true`) и сразу останавливаются при разрыве связи. В ответном пакете от ГУ передаётся 1 байт маски `telemetryDemand` (какие именно потоки `LOC` / `YAW` / `MAG` сейчас реально нужны ГУ исходя из выбранных `LocationSource`, `MockHeadingSource` и записи `geo-debug`), чтобы телефон не держал включённым GPS, когда на ГУ выбран только `PHONE_GYRO` при `LocationSource.TBOX`.
- Экран-инструкция «отключить оптимизацию батареи» (Xiaomi, Huawei, Samsung убивают службы).
- Переключатели на телефоне: «Отдавать геопозицию», «Отдавать гироскоп», «Отдавать компас». По умолчанию выключены.

### 5.2 Транспорт, раскладка пакетов и защита канала

Только прямой путь RFCOMM (`PhoneDirectWire`, `PhoneDirectLink` / `PhoneDirectServer`). Путь через ESP32 по BLE не подходит: интервал 200–300 мс, эфир делится с пультами.

Новые зашифрованные пакеты используют стандартный 24-байтный конверт `PhoneBleCodec` (`SEALED_LEN = 24`, полезная нагрузка `BODY_LEN = 11` байт) от телефона к ГУ. Поскольку полная точка GNSS не помещается в 11 байт, `LOC` передаётся двумя связанными 11-байтными страницами с общим номером поколения `gen` (собираются на ГУ аналогично `SnapshotAssembler`):

| Пакет | Период | Полезная нагрузка (`BODY_LEN = 11` байт) |
|-------|--------|------------------------------------------|
| `LOC_POS` | 1 с (частота `GPS_PROVIDER`) | `u8 gen`, `i32le latE7` (широта × $10^7$), `i32le lonE7` (долгота × $10^7$), `u16le hAccCm` (горизонтальная точность в см, `0xFFFF` — нет) |
| `LOC_MOTION` | 1 с (в паре с `LOC_POS`) | `u8 gen`, `i16le altM` (высота м, `0x7FFF` — нет), `u16le speedCms` (скорость см/с), `u16le bearingCdeg` (курс × 100°, `0xFFFF` — нет), `u8 sats` (`used` в младших 4 битах, `visible` в старших 4 битах), `u16le fixAgeMs` (возраст фикса на момент отправки по `elapsedRealtimeNanos`) |
| `YAW` | 100–200 мс | `u16le dtMs` (длительность окна), `i16le dPsiCdeg` ($\Delta\psi$ вокруг вертикали за окно в сотых градуса), `u16le monoLowMs` (младшие 16 бит `elapsedRealtime` конца окна), `u8 flags` (`bit0` = телефон неподвижен относительно машины, `bit1` = скачок акселерометра/гравитации), `u16le gravDeltaMg` (поворот/разброс вектора $\hat{g}$ за окно), `u16le reserved` |
| `MAG` | 1 с | `u16le magAzCdeg` (магнитный азимут в сотых градуса), `u16le fieldUt10` ($\|B\| \times 10$ мкТл), `u8 accuracy` (точность Android `0…3`), `i8 pitchDeg`, `i8 rollDeg` (наклон телефона), `u16le monoLowMs`, `u16le reserved` |

Телефон сам интегрирует гироскоп и шлёт приращения: десятки байт в секунду. Относительный возраст фикса `fixAgeMs` (вместо абсолютного UTC) избавляет от ошибки рассинхрона системных часов телефона и ГУ; для стыковки `YAW`/`MAG` ГУ ведёт скользящую оценку смещения монотонных часов (минимум задержки за окно).

Склонение (магнитный → истинный курс) считает ГУ через `android.hardware.GeomagneticField` по текущей позиции.

Правила канала, счётчиков и мультиплексирования:

1. **Строгий порядок счётчиков и окно anti-replay:** в `PhoneDirectLink` вызов `store.nextCounter()` и `PhoneBleCodec.seal(...)` выполняются **внутри** однопоточного `writer` непосредственно перед `outputStream.write`, чтобы высокочастотный поток `YAW` и нажатия кнопок UI (`CMD`/`REFRESH`) никогда не обгоняли друг друга по номеру счётчика. На стороне `PhoneDirectHost` добавляется скользящее окно anti-replay на 32 пакета (bitmask относительно `maxCounter`).
2. **Увеличенный блок резерва счётчиков (`PhoneStore`):** `COUNTER_BLOCK` увеличивается с `64L` до `512L` (или `1024L`), чтобы при потоке ~12 пакетов/с синхронный `SharedPreferences.commit()` на телефоне срабатывал не каждые 5 секунд, а раз в 1–1,5 минуты.
3. **Двусторонний heartbeat при выключенном экране телефона:** `PhoneDirectLink.recoverIfStale()` закрывает сокет, если от ГУ нет входящих пакетов дольше `PhoneBleLinkPolicy.LINK_STALE_MS` (12 с). Когда экран телефона выключен и UI не запрашивает полный `REFRESH`, `PhoneDirectServer` на ГУ в ответ на входящий поток `LOC`/`YAW`/`MAG` не реже раза в 5 с отправляет короткий зашифрованный ответ `TELEMETRY_ACK` (11 байт, включая `telemetryDemand`), поддерживая двустороннюю активность сокета.
4. **Один активный телефон-источник на ГУ:** `PhoneDirectServer` допускает до 3 подключений (`MAX_LINKS = 3`), но пакеты `LOC`/`YAW`/`MAG` для геопозиции и курса принимаются только от **одного** активного `phoneIdHex` (выбирается в настройках на ГУ или автоматически фиксируется за первым телефоном, приславшим телеметрию в текущей сессии), чтобы второй телефон в салоне не смешивал координаты и курс.

### 5.3 Гироскоп телефона

- ω_vert = ω · ĝ (проекция на единичный вектор гравитации): ориентация телефона в держателе не важна.
- Отбраковка: вектор гравитации в системе телефона повернулся больше порога или скачет акселерометр (`flags` / `gravDeltaMg` в `YAW`) — телефон в руке или упал; окно не учитывается, курс по цепочке подмены.
- Смещение нуля и масштаб калибруются на ГУ по GNSS-курсу только при движении вперёд (`!reverse`) так же, как для гироскопа ГУ (`GyroBiasStore`, `OnlineYawCalibEstimator`), но в отдельном хранилище.

### 5.4 Компас телефона

Пользователь проверял: компас телефона в машине правильно показывает север. Поэтому компас — полноценный отдельный источник, а не только поправка.

- **Сессионная калибровка установки телефона (`mountYawOffset`):** в отличие от жёстко закреплённого датчика на кузове, телефон в каждой поездке может ставиться в держатель под немного разным углом (или перекладываться на полку/в подстаканник). Поэтому угол установки (между осью телефона и осью машины) хранится как **сессионный** для текущей ориентации вектора гравитации $\hat{g}$:
  - калибруется автоматически по GNSS-курсу на первых 50–100 м прямолинейного движения вперёд (`!reverse`, `speed >= 15 км/ч`, малые `|steer|` и `|yaw|`);
  - если детектор §5.3 зафиксировал изменение вектора $\hat{g}$ относительно телефона (телефон взяли в руку или переставили), `mountYawOffset` сразу сбрасывается в `uncalibrated` и пересчитывается заново на ближайшей прямой.
- **Жёсткое железо машины:** опциональная поправка по секторам курса (8 секторов по 45°) применяется только поверх подтверждённого в текущей поездке `mountYawOffset` и сбрасывается при смене положения телефона.
- Отбраковка: точность Android < 2, |B| вне 25–65 мкТл (магнитный держатель, MagSafe, арматура), скачок |B| или азимута без поворота по колёсам и рулю, телефон в руке (§5.3) или не пройдена первичная привязка `mountYawOffset` после перестановки телефона.
- Сглаживание: медианный фильтр 3–5 с; в `PHONE_COMPASS` курс между сэмплами ведёт колёса / руль, компас подтягивает абсолютное значение.
- Стоянка: на неподвижной машине компас — единственный источник абсолютного курса; при старте счисления без GNSS (паркинг, тоннель) начальный курс берётся из компаса, если он не забракован и ориентация телефона не менялась с момента последней калибровки.

### 5.5 Геопозиция с телефона

- Новое значение `LocationSource.PHONE` рядом с `TBOX`, `ESP32`, `ANDROID`, `USB`.
- Пара `LOC_POS` + `LOC_MOTION` с одинаковым `gen` собирается в `LocValues` и идёт в тот же путь, что остальные внешние источники (подача в mock-позицию, режимы `MockCanSpeedMode`, `RoadMapMatcher`).
- За счёт использования на телефоне сырого `GPS_PROVIDER` (а не `FusedLocationProvider`) исключается двойной map-matching и «прилипание» координат на развилках перед нашим `RoadMapMatcher`.
- Пропадание телефона или отсутствие новых пар `LOC` дольше порога свежести (~3 с) = потеря фикса: работают удержание и счисление как при пропадании GNSS.
- Интеграция с внешними контрактами: в сигнал `geo_source` внешнего HTTP API ([EXTERNAL_API_RU.md](EXTERNAL_API_RU.md)) и автоматизаций ([AUTOMATIONS_AI_JSON_GUIDE_RU.md](AUTOMATIONS_AI_JSON_GUIDE_RU.md)) добавляется значение `phone`, а в скрытую опору `truth.src` журнала `geo-debug` ([GEO_DEBUG_LOG_RU.md](GEO_DEBUG_LOG_RU.md)) — источник `phone`.

## 6. ГУ: интерфейс и диагностика

- Экран геопозиции: выбор источника курса с пометкой «недоступно: причина»; статус активного источника и подмены; для телефона — какой телефон выбран активным источником (при нескольких подключённых по RFCOMM), связь, возраст пакетов, статус калибровки установки (`mountYawOffset`), точность компаса, |B|.
- `DrSensorRepository` / `AndroidSensorDrBackend`: показывать отказ HAL явно («сенсорный HAL отказал в активации»), а не пустые значения. Признак — подписка зарегистрирована, а сэмплов нет дольше 3 с.
- Geo-debug (`GeoDebugLogRecorder`, `tools/geo_debug_analyze.py`): новые поля — Δψ колёс, ω_lat, ω телефона, азимут компаса, |B|, `mountYawOffset`, источник курса на каждом тике, причины отбраковки, `truth.src=phone`.
- Калибровки (колея, гироскоп телефона, установка телефона, сектора компаса) — в экран калибровок рядом с рулём и гироскопом, со сбросом.

## 8. Риски

- Импульсы колёс на A10 через VHAL могут приходить редко (`ON_CHANGE`, батчи MCU) — проверить на этапе 0.
- Компас: магнитные держатели, рамы сидений, кабели питания рядом с телефоном; мосты, трамвайные пути, паркинги; смена положения телефона в держателе (решается автосбросом `mountYawOffset` по скачку вектора гравитации $\hat{g}$).
- Телефон: энергосбережение производителей, нагрев, разряд без зарядки, разрывы Bluetooth, запрет фонового старта FGS `location` на Android 14+ без `ACCESS_BACKGROUND_LOCATION`. Телефон — дополнительный источник, база — CAN; GPS и сенсоры телефона включаются только при живом RFCOMM и запросе `telemetryDemand` от ГУ.
- RFCOMM на A9/A10 проверен вместе с HFP и A2DP, но поток каждые 100–200 мс на долгой поездке (в том числе при звонке SCO и параллельном опросе ELM327) требует проверки устойчивости буфера чтения и скользящего окна счётчиков.
