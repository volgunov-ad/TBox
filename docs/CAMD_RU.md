# Камеры ГУ (`:camd`)

Отдельное приложение `vad.dashing.camd`. Ему отдают команды TBox Monitor и нештатный лаунчер DCL. Само оно не встроено ни в одно из них.

Факты про головное устройство: [CAMERAS_A9_RU.md](CAMERAS_A9_RU.md). Сокет `ais_server` пускает только root. Один вход камеры держит один клиент. Штатный процесс `AVMapp` уже держит входы 4, 5, 8 и 9. `avm_sharecamera` и callback SDK — уже обработанный кадр с наложенными элементами, для окон и записи его не используем. Нужен чистый кадр сенсора, буфер `qcarcam_get_frame`.

## Зачем

Сейчас нужна служба с API: TBox Monitor и DCL просят показать или убрать окно любой камеры в любом месте экрана. Картинка — чистый кадр сенсора, не `avm_sharecamera`.

Видеорегистратор отложен. Когда до него дойдёт очередь, та же служба будет кодировать те же кадры. Папка, частота, предел одного файла и общий предел настраиваются. Запись начинается вместе с системой, только если она включена, и дописывает файл при остановке. Контейнер — фрагментированный MP4: обычный MP4 пишет оглавление в конце, и обрыв питания оставляет ролик, который не открывается.

## Как устроено

Два слоя.

**Обычный процесс** хранит настройки, рисует экран и слушает `127.0.0.1:8770`. К `ais_server` он не подключается. Порт `8765` занят TBox Monitor, `8766` — локальным статусом TBox MQTT. Ошибка прослушивания не должна закрывать экран.

**Root-демон** — shell-скрипт, который `mb_daemon` поднимает один раз ([HEAD_UNITS_DEVICE_NOTES_RU.md](HEAD_UNITS_DEVICE_NOTES_RU.md) §10). Скрипт взвода заканчивается сразу, демон остаётся. Пока он жив, раз в секунду обновляет `/data/local/tmp/camd.pid` и читает команду из каталога приложения. Команда «открыть» — это XML окна и запуск `/system/bin/qcarcam_test`. «Закрыть» — завершение этого процесса.

`qcarcam_test` читает положение окна один раз при старте. Сдвиг — новый запуск, картинка на короткое время пропадает. Имеет смысл отдельно проверить, двигает ли `test_util_set_window_param` уже открытое окно. Если да, перезапуск для сдвига не нужен. Кнопка «Открыть» считает успехом живой процесс через секунду после старта. Кадр она не ждёт, поэтому пустое окно тоже выглядит как успех. «Закрыть» только убивает процесс.

`qcarcam_test` рисует слой SurfaceFlinger `qcarcam_0` в контейнере `Display Overlays`, поверх лаунчера. Без кадра слой прозрачный. На стенде `192.168.1.128` камеры не подключены, поэтому нулевой `Average FPS` там ничего не говорит о машине.

`qcarcam_test` не видеорегистратор и не служба для TBox и DCL. Его `-dumpFrame` пишет несколько сырых кадров в `/data/vendor/camera/frame_%d_%i.raw`. Пока он держит вход, второй клиент тот же буфер не получит. После строки `Aborted` процесс сам не завершается: проба убивает его через 22 секунды и только потом делает `ctl.start AVMapp`.

Дальше окно рисует своя root-служба, клиент `ais_server`. Она одна держит чистый кадр и по API `127.0.0.1:8770` показывает его поверх всего. `qcarcam_test` из `mb_daemon` кадр получает, но буфер на экран не отдаёт: после первого кадра `qcarcam_release_frame` возвращает 13, а у задней камеры `Dequeuebuffer` возвращает −38. В том же логе `mb_daemon` не может нормально вызвать `surfaceflinger`. Слой `qcarcam_0` создаётся и остаётся пустым. Служба должна класть кадр в окно из процесса, которому SurfaceFlinger отдаёт буфер. Это обычное окно Android поверх лаунчера, место и размер задаёт команда API.

`AVMapp` на время показа входов 4, 5, 8 и 9 должен их отпустить. `com.mengbo.avm` — только оболочка. Служба init называется `AVMapp` (`/vendor/etc/init/hw/init.JETOUR.rc`): её поднимает `vendor.camera.mbhal.type=1` вместе с `vendor.cartype.version` 3 или 7. Остановка — `setprop ctl.stop AVMapp`, возврат — `setprop ctl.start AVMapp`. Пока `AVMapp` остановлен, заднюю камеру на задней передаче открывает наша служба.

## План

1. Демон и одно окно через `qcarcam_test`. Сделано как каркас. На машине картинки не даёт.
2. Пробы на машине: живой `AVMapp` и `ctl.stop AVMapp`. Сделано 10 ноября 2026, результат ниже.
3. Служба с API для TBox Monitor и DCL. Несколько окон сразу: на каждую камеру не больше одного. Чистый кадр, поверх лаунчера, место и размер задаёт команда. В углу каждого окна крупный крестик, его удобно нажать пальцем; он закрывает только это окно. Повторный `OPEN` той же камеры не создаёт второе окно, а переносит уже открытое. Для входов 4, 5, 8 и 9 служба останавливает `AVMapp`, пока открыто хотя бы одно из этих окон, и включает его снова, когда закрыто последнее. Задняя передача при остановленном `AVMapp` открывает вход 5 сама, если его окно ещё не показано.
4. Подключить вызовы API в TBox Monitor и в DCL.
5. Потом, отдельно: видеорегистратор на тех же кадрах. Фрагментированный MP4, папка, частота, предел одного файла и общий предел, старт с загрузки только если запись включена, дописывание файла на остановке.

## Пробы на машине

Нужна сборка с кнопками проб (`ProbeScripts`), не пакет от 6–7 ноября. APK: `camd/build/outputs/apk/debug/camd-debug.apk`. На стоянке, экран перед глазами:

```
adb install -r -d camd-debug.apk
```

В **Камеры ГУ** выбрать вход и нажать по очереди:

1. **Проба, AVM работает.** `AVMapp` не трогается. 20 секунд большое окно по центру (60 % экрана, не ползунки).
2. **Проба, AVM остановлен.** `setprop ctl.stop AVMapp`, те же 20 секунд, при выходе скрипта `setprop ctl.start AVMapp`. Задней картинки в эту минуту нет.

Логи в `/sdcard/Download`:

| Кнопка | Файл |
|---|---|
| AVM работает | `camd-probe-nostop-<вход>-<дата>.txt` |
| AVM остановлен | `camd-probe-stopavm-<вход>-<дата>.txt` |

`qcarcam_test` после сообщения `Aborted` сам не завершается. Проба через 22 секунды убивает его и только потом снова делает `ctl.start AVMapp`, иначе штатная камера осталась бы выключенной.

Как читать:

- Живая картинка в центре и `Average FPS` больше нуля. Чистый кадр есть. Если это было при живом AVM, отключать его не нужно.
- Картинки нет и `Average FPS: 0.00`. Кадр не пришёл. На пробе без остановки это значит, что вход занят. На пробе с остановкой — что и без AVM поток не пошёл.
- `AVMapp` снова в `ps` до конца 20 секунд второй пробы. Его перезапустили, проверка не считается.

## Что сделано

Каркас шага 1 и кнопки проб шага 2. Отладочный APK с пробами собран (`:camd:assembleDebug`), модульные тесты прошли. На стенде `192.168.1.128` камер нет: приложение открывается, `qcarcam_test` создаёт слой `qcarcam_0`, кадров оттуда нет. На машине кнопкой «Открыть» процесс стартовал без картинки; логов `camd-probe-*.txt` с той поездки нет.

| | |
|---|---|
| Приложение | `vad.dashing.camd`, имя «Камеры ГУ», модуль `:camd` |

## Чего ещё нет

- Служба, которая сама клиент `ais_server` и рисует кадр в своих окнах поверх лаунчера. На каждую камеру одно окно. В углу крупный крестик, он закрывает только это окно. `qcarcam_test` для показа не подходит: кадр есть, на экране его нет.
- Остановка `AVMapp`, пока открыто хотя бы одно окно входов 4, 5, 8 и 9, и включение его снова, когда закрыто последнее.
- Задняя камера на задней передаче, пока `AVMapp` остановлен и окно входа 5 ещё не открыто.
- Команды `OPEN` и `CLOSE <id>`, которые вызывают TBox Monitor и DCL. Сейчас сокет `127.0.0.1:8770` есть, к нему никто не подключён, а «Открыть» запускает `qcarcam_test`.
- Сдвиг окна без перезапуска клиента. Повторный `OPEN` той же камеры должен переносить существующее окно.
- Живой список входов с ГУ. Сейчас список зашит.
- Токен на API. Сейчас любой локальный процесс может послать команду.
- Видеорегистратор. Отложен до рабочих окон.
