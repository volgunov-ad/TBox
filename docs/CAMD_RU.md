# Камеры ГУ (`:camd`)

Отдельное приложение `vad.dashing.camd`. Ему отдают команды TBox Monitor и нештатный лаунчер DCL. Само оно не встроено ни в одно из них.

Инструкция вендору DCL по TCP API окон: [DCL_CAMD_CAMERA_API_FOR_VENDOR_RU.md](DCL_CAMD_CAMERA_API_FOR_VENDOR_RU.md). Факты про головное устройство: [CAMERAS_A9_RU.md](CAMERAS_A9_RU.md). Сокет `ais_server` пускает только root. Один вход камеры держит один клиент. Штатный процесс `AVMapp` уже держит входы 4, 5, 8 и 9. `avm_sharecamera` и callback SDK — уже обработанный кадр с наложенными элементами, для окон и записи его не используем. Нужен чистый кадр сенсора, буфер `qcarcam_get_frame`.

## Зачем

Сейчас нужна служба с API: TBox Monitor и DCL просят показать или убрать окно любой камеры в любом месте экрана. Картинка — чистый кадр сенсора, не `avm_sharecamera`.

Видеорегистратор отложен. Когда до него дойдёт очередь, та же служба будет кодировать те же кадры. Папка, частота, предел одного файла и общий предел настраиваются. Запись начинается вместе с системой, только если она включена, и дописывает файл при остановке. Контейнер — фрагментированный MP4: обычный MP4 пишет оглавление в конце, и обрыв питания оставляет ролик, который не открывается.

## Как устроено

Два процесса.

**Окно** — обычный процесс `vad.dashing.camd`. Он слушает `127.0.0.1:8770`, рисует по одному окну `TYPE_APPLICATION_OVERLAY` на камеру и читает последний кадр из файла. К `ais_server` он не подключается: из обычного процесса `libais_client.so` не открывается, а рисовать из `mb_daemon` эта ГУ не даёт. Порт `8765` занят TBox Monitor, `8766` — локальным статусом TBox MQTT. Клиентский сокет закрывается по таймауту 5 с: полузакрытые соединения не копят fd. Командный демон `camd-daemon.sh` с очередью `camd.cmd` удалён: окнами управляет только этот процесс.

**Чтение кадра** — root-программа `camd_grab`. `mb_daemon` поднимает её коротким скриптом и сразу отпускается. Программа остаётся root, открывает `libais_client.so` и `/dev/ion`, вызывает `qcarcam_get_frame`, копирует сырой UYVY в общий файл `/mnt/camd-ram/camd-uyvy-<id>` (tmpfs, два слота, заголовок 64 байта) и сразу отпускает кадр камеры. Окно рисует этот буфер шейдером, без прохода по пикселям на главном потоке. Список нужных камер она читает из `grab.desired` в каталоге приложения, раз в 250 мс; `beat` в `/data/local/tmp/camd-grab.beat` пишется раз в секунду; ожидание кадра — 15 мс. Повторный `OPEN` той же камеры файл не трогает: окно только переносится. В углу окна крестик 88 dp, он закрывает только это окно через один поток `camd-close`.

Деплой `camd_grab`: приложение копирует бинарник из assets в `files/camd_grab.new`, скрипт перезапуска останавливает старый процесс, копирует его в `/data/local/tmp/camd_grab` и пишет версию в `/data/local/tmp/camd_grab.ver`. Старый root-процесс переживает переустановку APK и держит `beat` свежим, поэтому перед повторным использованием сверяется версия: не совпала — бинарник перезаливается, даже если `beat` ещё тёплый.

Для входов 4, 5, 8 и 9 тот же скрипт делает `setprop ctl.stop AVMapp` до старта клиента. Когда закрыто последнее такое окно, скрипт делает `setprop ctl.start AVMapp`.

Раскладка структур `libais_client.so` взята по символам этой ГУ (`qcarcam_get_frame` из четырёх аргументов, `qcarcam_release_frame(hndl, idx)`, версия `0x404`, цвет UYVY `0x07080102`) и по образцу, где в `p_buf` лежит fd ION. Заголовка этой библиотеки в дереве нет. На стенде без камер можно проверить, что процесс жив и `AVMapp` возвращается. Кадр проверяется только на машине.

`qcarcam_test` из приложения больше не вызывается: командный демон и кнопки проб удалены 13 ноября 2026 (история — в git до коммита `bbf82743`). Он кадр получает, но из `mb_daemon` на экран его не кладёт: после первого кадра `qcarcam_release_frame` возвращает 13, у задней камеры `Dequeuebuffer` возвращает −38. После строки `Aborted` процесс сам не завершается: проба убивала его через 22 секунды и только потом делала `ctl.start AVMapp`.

`AVMapp` на время показа входов 4, 5, 8 и 9 должен их отпустить. `com.mengbo.avm` — только оболочка. Служба init называется `AVMapp` (`/vendor/etc/init/hw/init.JETOUR.rc`). Остановка — `setprop ctl.stop AVMapp`, возврат — `setprop ctl.start AVMapp`. Задняя передача, пока `AVMapp` остановлен и окно входа 5 ещё не открыто, в эту сборку не входит: штатная задняя картинка вернётся вместе с `AVMapp`.

## План

1. Демон и одно окно через `qcarcam_test`. Сделано как каркас. На машине картинки не даёт.
2. Пробы на машине: живой `AVMapp` и `ctl.stop AVMapp`. Сделано 10 ноября 2026, результат ниже.
3. Служба с API. Сделано в коде, на машине ещё не проверено. Несколько окон сразу: на каждую камеру не больше одного. Чистый кадр, поверх лаунчера, место и размер задаёт команда. В углу каждого окна крупный крестик. Повторный `OPEN` той же камеры переносит уже открытое окно. Для входов 4, 5, 8 и 9 служба останавливает `AVMapp`, пока открыто хотя бы одно из этих окон, и включает его снова, когда закрыто последнее. Задняя передача при остановленном `AVMapp` в эту сборку не входит.
4. Подключить вызовы API в TBox Monitor и в DCL.
5. Потом, отдельно: видеорегистратор на тех же кадрах. Фрагментированный MP4, папка, частота, предел одного файла и общий предел, старт с загрузки только если запись включена, дописывание файла на остановке.

- Живая картинка в центре и `Average FPS` больше нуля. Чистый кадр есть. Если это было при живом AVM, отключать его не нужно.
- Картинки нет и `Average FPS: 0.00`. Кадр не пришёл. На пробе без остановки это значит, что вход занят. На пробе с остановкой — что и без AVM поток не пошёл.

## Надёжность, 13 ноября 2026

Ветка `fix/camd-robustness`. Проблемы нашли разбором кода, исправления поэтапно проверяли на стенде `192.168.1.128:5555` (камер нет):

- зависший `chmod`/`setprop` больше не вешает `OPEN`/`CLOSE` навсегда: вывод команды сливается в отдельном потоке, `waitFor` с таймаутом (`CamdShell`);
- полузакрытые TCP-клиенты закрываются сами через 5 с и не текут fd;
- `seq=N` в статусе сравнивается по целому токену, а не по подстроке;
- таблица окон — `ConcurrentHashMap`: поток API читает её параллельно с main-потоком;
- поток отрисовки останавливается по токену поколения: `onSurfaceTextureDestroyed` всегда отдаёт текстуру, join 1 с, «воскресший» старый поток исключён; отрисовка паркуется, пока окно отцеплено от окна;
- контроллер экрана глушит executor и поток опроса в `onDestroy`;
- крестик окна ходит в один поток `camd-close`, а не создаёт поток на нажатие;
- `getprop` идёт через `CamdShell` с кэшем 2 с; `waitProp` читает напрямую и сбрасывает кэш;
- START-команда вынесена в `StartReceiver` под signature-разрешение; `BootReceiver` принимает только системные (protected) broadcast'и; `WRITE_EXTERNAL_STORAGE` — только до Android 9;
- мёртвый код удалён: командный демон, `ProbeScripts`, `WindowXml`, очередь `camd.cmd`;
- рендер: свежесть общего файла — один `Os.stat` вместо `open+fstat` на каждую итерацию, пауза 8 мс, кадр льётся в текстуру прямо из mmap без CPU-копии;
- `camd_grab`: `FRAME_TIMEOUT_NS` 100→15 мс, `beat` раз в секунду, `grab.desired` раз в 250 мс, рабочий `usleep` 1→4 мс, tmpfs 32→48 МБ.

На стенде проверено: `OPEN`/`CLOSE`/`STATUS`, окна 4 и 5, `AVM OFF` → `AVMapp` `running`, `AVM ON` → снова `stopped`, idle-клиент закрылся на 5-й секунде, force-stop и перезапуск, перезагрузка: автостарт поднял службу и API, впустую `camd_grab` не стартует, полный цикл окон с чистой загрузки. Картинки на стенде нет — окна проверены только до надписи «жду кадр».
