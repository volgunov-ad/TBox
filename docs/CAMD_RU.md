# Камеры ГУ (`:camd`)

Отдельное приложение `vad.dashing.camd`. Ему отдают команды TBox Monitor и нештатный лаунчер DCL. Само оно не встроено ни в одно из них.

Факты про головное устройство: [CAMERAS_A9_RU.md](CAMERAS_A9_RU.md). Сокет `ais_server` пускает только root. Один вход камеры держит один клиент. Штатный процесс `AVMapp` уже держит входы 4, 5, 8 и 9. `avm_sharecamera` и callback SDK — уже обработанный кадр с наложенными элементами, для окон и записи его не используем. Нужен чистый кадр сенсора, буфер `qcarcam_get_frame`.

## Зачем

1. Открывать окно с любой камерой в любом месте экрана.
2. Писать сжатое видео в выбранную папку, если запись включена. Папка, частота кадров, предел одного файла и предел всех файлов записи настраиваются. Запись начинается вместе с системой и заканчивается вместе с ней. Файл после остановки должен открываться.

## Как устроено

Два слоя.

**Обычный процесс** хранит настройки, рисует экран и слушает `127.0.0.1:8770`. К `ais_server` он не подключается. Порт `8765` занят TBox Monitor, `8766` — локальным статусом TBox MQTT. Ошибка прослушивания не должна закрывать экран.

**Root-демон** — shell-скрипт, который `mb_daemon` поднимает один раз ([HEAD_UNITS_DEVICE_NOTES_RU.md](HEAD_UNITS_DEVICE_NOTES_RU.md) §10). Скрипт взвода заканчивается сразу, демон остаётся. Пока он жив, раз в секунду обновляет `/data/local/tmp/camd.pid` и читает команду из каталога приложения. Команда «открыть» — это XML окна и запуск `/system/bin/qcarcam_test`. «Закрыть» — завершение этого процесса.

`qcarcam_test` читает положение окна один раз при старте. Сдвиг — новый запуск, картинка на короткое время пропадает. Имеет смысл отдельно проверить, двигает ли `test_util_set_window_param` уже открытое окно. Если да, перезапуск для сдвига не нужен. Кнопка «Открыть» считает успехом живой процесс через секунду после старта. Кадр она не ждёт, поэтому пустое окно тоже выглядит как успех. «Закрыть» только убивает процесс.

`qcarcam_test` рисует слой SurfaceFlinger `qcarcam_0` в контейнере `Display Overlays`, поверх лаунчера. Без кадра слой прозрачный. На стенде `192.168.1.128` камеры не подключены, поэтому нулевой `Average FPS` там ничего не говорит о машине.

`qcarcam_test` не видеорегистратор. Его `-dumpFrame` пишет несколько сырых кадров в `/data/vendor/camera/frame_%d_%i.raw` и не умеет ни сжатия, ни папки, ни ротации. Пока процесс теста держит вход, второй программе тот же буфер не отдать.

Запись и окно будет делать одна своя root-служба, клиент `ais_server`. Она забирает чистые кадры, по API кладёт выбранную камеру в окно поверх всего и, если запись включена, кодирует те же кадры. `AVMapp` на это время вход должен отдать. Иначе чистого кадра нет ни на экране, ни в файле. `com.mengbo.avm` — только оболочка. Служба init называется `AVMapp` (`/vendor/etc/init/hw/init.JETOUR.rc`): её поднимает `vendor.camera.mbhal.type=1` вместе с `vendor.cartype.version` 3 или 7. Остановка — `setprop ctl.stop AVMapp`, возврат — `setprop ctl.start AVMapp`. Пока `AVMapp` остановлен, заднюю камеру на задней передаче должна открывать наша служба.

Запись, когда до неё дойдёт, делает эта же служба. Контейнер — фрагментированный MP4 (H.264): обычный MP4 пишет оглавление в конце, и обрыв питания оставляет ролик, который не открывается. Кусок в 1–2 секунды уже целый, при жёстком выключении пропадает только незакрытый хвост. На `SIGTERM` служба дописывает текущий кусок и закрывает файл. Жёсткое снятие питания без сигнала хвост всё равно обрежет — это проверяется выключением зажигания.

Пока запись выключена, демон ради неё камеру не открывает. Окна по команде от записи не зависят.

Чужие файлы в папке не удаляются. Ротация смотрит только на свои имена: новый файл по достижении предела одного файла, затем самые старые свои, пока сумма не уложится в общий предел. Частота записи — выбрасывание лишних кадров. Сенсор здесь около 25 к/с, выше него запись не пойдёт.

## План

1. Демон и одно окно: список камер, открыть в заданной точке, закрыть, открыть в другой точке.
2. На машине проверить, отдаёт ли `qcarcam_test` чистый кадр при живом `AVMapp` и после `ctl.stop AVMapp`. Логи проб лежат в «Загрузках».
3. Своя root-служба вместо `qcarcam_test`: единственный клиент входа, окно поверх всего по API, задняя камера на задней передаче.
4. Запись одного входа: фрагментированный MP4, оба предела размера, частота кадров, включение, старт с загрузки, `SIGTERM` оставляет играбельный файл. Затем проверка обрывом питания.
5. Несколько камер в записи и несколько окон сразу.
6. Подключить API к TBox Monitor и к DCL.

## Пробы на машине

Нужна сборка с кнопками проб (`ProbeScripts`), не пакет от 6–7 ноября. APK: `camd/build/outputs/apk/debug/camd-debug.apk`. На стоянке, экран перед глазами:

```
adb install -r -d camd-debug.apk
```

В **Камеры ГУ** выбрать вход и нажать по очереди:

1. **Проба, AVM работает.** `AVMapp` не трогается. 20 секунд большое окно по центру (60 % экрана, не ползунки).
2. **Проба, AVM остановлен.** `setprop ctl.stop AVMapp`, те же 20 секунд, при выходе скрипта `setprop ctl.start AVMapp`. Задней картинки в эту минуту нет.

Логи в `/sdcard/Download`:

| Кнопка | Файл |
|---|---|
| AVM работает | `camd-probe-nostop-<вход>-<дата>.txt` |
| AVM остановлен | `camd-probe-stopavm-<вход>-<дата>.txt` |

Лог создаётся в `/sdcard/Download` до остановки `AVMapp` и до запуска `qcarcam_test`. Туда же пишется `logcat` тега `qcarcam_test`. Сам `/sdcard/autorun.sh` только запускает пробу в фоне и сразу заканчивается, чтобы следующая проба не ждала зависший `qcarcam_test`. Если кнопка вернула таймаут, свежий `camd-probe-*.txt` в «Загрузках» всё равно нужно забрать.

Как читать:

- Живая картинка в центре и `Average FPS` больше нуля. Чистый кадр есть. Если это было при живом AVM, отключать его не нужно.
- Картинки нет и `Average FPS: 0.00`. Кадр не пришёл. На пробе без остановки это значит, что вход занят. На пробе с остановкой — что и без AVM поток не пошёл.
- `AVMapp` снова в `ps` до конца 20 секунд второй пробы. Его перезапустили, проверка не считается.

## Что сделано

Каркас шага 1 и кнопки проб шага 2. Отладочный APK с пробами собран (`:camd:assembleDebug`), модульные тесты прошли. На стенде `192.168.1.128` камер нет: приложение открывается, `qcarcam_test` создаёт слой `qcarcam_0`, кадров оттуда нет. На машине кнопкой «Открыть» процесс стартовал без картинки; логов `camd-probe-*.txt` с той поездки нет.

| | |
|---|---|
| Приложение | `vad.dashing.camd`, имя «Камеры ГУ», модуль `:camd` |
| Экран | выбор входа 0, 1, 3, 4, 5, 8, 9; ползунки X, Y, ширина, высота в долях экрана; «Открыть» и «Закрыть»; две пробы по 20 секунд с логом в `/sdcard/Download` |
| Предупреждение | у входов 4, 5, 8, 9 написано, что их держит штатный AVM. Кнопка их всё равно открывает |
| Демон | `camd-daemon.sh` в каталоге приложения. Взвод через `/sdcard/autorun.sh` и `vendor.autorun.sdcard.logfile`. Повторный взвод при живом pid выходит |
| Окно | один `qcarcam_test -config=… -seconds=86400 -nonInteractive`. Новое «Открыть» убивает предыдущий процесс. Само закроется через сутки |
| Разрешение кадра | из штатных XML: 0 — 1488×616, 1 — 1280×720, остальные из списка — 1280×800 |
| API | `127.0.0.1:8770`, одна строка запроса и одна ответа: `OPEN <id> <x> <y> <w> <h>`, `CLOSE`, `STATUS`. Ответ `OK state=…` или `ERR bad_command`. `8766` не используется: его слушает TBox MQTT |
| Загрузка | `BOOT_COMPLETED` стартует службу и API. Демон поднимается при первой команде, если выдано право записи на `/sdcard` |
| Код | `camd/src/main/java/vad/dashing/camd/`, пробы в `ProbeScripts.kt` |
