# План: BLE-реле на ESP32 (плата ESP32_Relay X1_V1.2)

Статус: план утверждён (вариант A), компаньон — fw 0.13.0, прошивка реле — новый проект `firmware/esp32-relay`.

## 1. Железо

- Плата «ESP32_Relay X1_V1.2», модуль **ESP32-WROOM-32E**, классический ESP32 (не S3).
- Одно реле Songle-класса, **активный высокий** уровень управления, «сухой контакт» NO/COM —
  управление нагрузкой гальванически развязано от логики.
- Питание — от бортовой 12 В через DC-DC на плате. Перед монтажом сверить диапазон входа
  DC-DC по шёлкографии (9–24 В вход покрывает и 12 В сети, и просадки стартера).
- GPIO реле по маркировке не определяется однозначно → в прошивке каркаса есть **probe-режим**
  (см. §5.7), найденный пин фиксируется в Kconfig.
- Выбор точки питания (ACC или постоянный +12 В) — решение при монтаже:
  - постоянный +12 В: состояние «держать» живёт без ограничений, reboot'ы реле редки;
  - ACC: реле перезагружается при каждом включении зажигания — восстановление последнего
    состояния из NVS (флаг `restored` в первом 0x31) покрывает этот сценарий.

Применение сухого контакта:
- **эмуляция кнопки**: COM+NO параллельно физической кнопке; импульс `pulse_ms` = нажатие;
- **произвольная нагрузка**: COM/NO в разрыв цепи питания нагрузки (10 А / 250 В AC — с запасом
  только для маломощных цепей).

## 2. Архитектура (вариант A — GATT-клиент к сервису телефона компаньона)

Реле — NimBLE GATT-**клиент**, подключается к существующему сервису телефона компаньона:

- Advertising компаньона: имя «TBox», complete UUID16 list `0x7B0E`, интервал 100–200 мс
  (`ble_phone.c:start_adv_locked`).
- Сервис `0x7B0E`: write `0x7B0F` (WRITE | WRITE_NO_RSP, максимум 64 байта), notify `0x7B10`.
- Реле сканирует по имени «TBox» + UUID16 `0x7B0E`, подключается, обменивается MTU
  (запрашивает 64; протоколу хватает ≥ 27 = 24 + 3 ATT-заголовка — гейт `mtu >= SEALED_LEN+3`),
  подписывается на CCCD `0x7B10`, дальше весь обмен — те же 24-байтные пакеты, что у телефона.
- Интервал соединения остаётся 200–300 мс (`PHONE_ITVL_MIN/MAX`) — окно сканирования Shelly
  (40 мс каждые 80 мс) не деградирует. Задержка команды реле 0.2–0.6 с — приемлема (подтверждено).
- Пара «реле ↔ компаньон» = одна запись в общем списке `BLE_DEVICE_MAX = 20` (делится с
  BLE-кнопками через `ble_btn_mac_count()`). 2–3 платы — штатно помещаются.
- Одновременные соединения: `PHONE_LINK_MAX` 3 → **5**, `CONFIG_BT_NIMBLE_MAX_CONNECTIONS`
  3 → **5** (см. §4).

Телефонное приложение **не трогаем** (MVP: управление только с ГУ). Телефон при шумах в эфире
ничего не теряет: компаньон кладёт 0x30 только в tx-очередь линка реле, страницы 0x2x — только
в очереди линков телефонов; входящие типы телефон не знает и на свои 2/3 от реле не дождётся.
Реле и телефон физически не могут получить чужой пакет — очереди per-link (`phone_link_t.tx`).

## 3. Протокол

### 3.1 Сопряжение (PAIR) — cleartext, новый тип 0x11

Телефонный PAIR — открытый текст, тип `1`: `type(1) id(4) key(16) name(..26)`, длина ≥ 21
(`on_pair_packet`). Для реле вводится тип **`0x11`** с тем же телом:

```
байт 0:      0x11
байты 1..4:  id — 4 случайных байта, генерируются при первом включении (NVS)
байты 5..20: key — 16 случайных байтов (NVS)
байты 21+:   имя, ≤ 26 байт (по умолчанию «Relay-XX» из двух младших байтов id)
```

- Пишется реле в `0x7B0F` раз в ~1 с, **пока в компаньоне открыто окно обучения**
  (`ble_phone_learn_begin`, 60–120 с; `s_learn`).
- Компаньон показывает на ГУ тот же диалог «да/нет» (`phonePair`/`allow`/`deny`), привязка
  записи происходит в `ble_phone_allow` (pending-pair), запись помечается `kind=1` (реле).
- Повторный PAIR от уже сопряжённого id с тем же key — игнор (как у телефона); с новым key —
  диалог перевыпуска ключа, счётчик входящих сбрасывается в 0 (как у телефона).
- PAIR вне окна обучения молча отбрасывается (гейт `!s_learn` уже есть в `on_pair_packet`).

### 3.2 Запечатанные пакеты — формат не меняется (24 байта)

```
[0]      type
[1..4]   id
[5..8]   counter (u32 LE) ^ mask, mask = первые 4 байта AES-128-ECB(key, id||type||0xA5||0×11)
[9..19]  body (11 байтов), AES-128-CTR, nonce = id||type||counter LE||0xC7||0×7
[20..23] HMAC-SHA256(key, type||id||counter LE||body), первые 4 байта
```

Занятые типы компаньона: 1 (PAIR cleartext), 2 (команда телефона), 3 (REFRESH-запрос),
4+0x2x (страницы snapshot к телефону). Новые:

**0x30 RELAY_CMD — компаньон → реле (notify):**

```
body[0]   маска каналов (реле X1: только бит 0)
body[1]   биты состояний: 1 = замкнуть, 0 = разомкнуть (для битов из body[0])
body[2..3] pulse_ms, u16 LE; 0 = держать состояние, >0 = импульс
body[4]   gen — эхо-байт для сопоставления 0x31 с командой
body[5..10] резерв, 0
```

**0x31 RELAY_STATE — реле → компаньон (write в 0x7B0F):**

```
body[0]   фактическая маска замкнутых каналов
body[1]   флаги: bit0 applied (команда применена), bit1 restored (восстановлено после
          загрузки), bit2 pulse-active (идёт импульс)
body[2..3] uptime_s, u16 LE (модуль 65536)
body[4]   gen — эхо gen из 0x30
body[5..10] резерв, 0
```

Реле отправляет 0x31: после каждой 0x30 и **каждые 10–15 с как keepalive** — иначе
`LINK_IDLE_MS = 20000` (`ble_phone.c:47`) оборвёт «молчащий» линк. Тайминг keepalive
12 с ± рандом 2 с, чтобы несколько реле не сбивались в фазу.

Гейт `unseal` (`ble_phone.c:428`) принимает только `type ∈ {2,3,4}` → компаньон расширяет
его на **0x31 только для записей kind=1**. 0x30 компаньон только шлёт (seal), входящим не бывает.

### 3.3 Счётчики

Правила как у телефона (защита от replay, монотонность per-направление):

- **Реле, tx** (пакеты 0x31): u32 в NVS. При загрузке, если хоть один пакет был отправлен,
  счётчик **сдвигается на +4096** (`margin`): питание срезают без shutdown, NVS может не
  сохранить последние записи. Кэш записи в NVS — не чаще `RELAY_COUNTER_SAVE_MS = 10 с`
  (аналог `COUNTER_SAVE_MS`).
- **Реле, rx** (пакеты 0x30): последний принятый counter в NVS, пакет с `counter <= saved`
  отбрасывается; запись с троттлингом 10 с.
- **Компаньон, tx к реле** (0x30): на запись реле заводится отдельный NVS-ключ `r%d`
  (по индексу записи, рядом с `c%d` входящих). Пишется **при каждой отправке** 0x30 — их
  единицы в минуту, износ NVS ничтожен в сравнении со snapshot-страницами.
- **Компаньон, rx от реле** (0x31): существующий counter записи (`c%d`), `counter <= stored`
  → отброс; инкремент и троттлинг записи — как у телефона.

Компаньон держит желаемую маску каждого реле в RAM (в записи линка) и **пересылает её при
каждом (пере)подключении реле** — реле перезагрузилось/переподключилось → состояние вернулось.
Хранить маску в NVS не нужно: она восстанавливается на самом реле из его NVS, а компаньон
синхронизирует актуальное значение при линке.

### 3.4 Записи устройств

`phone_rec_t` (51 байт blob: id[4] key[16] counter[4] name_len[1] name[26]) дополняется
байтом **kind**: 0 = телефон, 1 = реле. Новый `PHONE_REC_LEN = 52`, kind — байт 51
(ранее не существовал). Старые блобы длиной 51 при загрузке трактуются как kind=0.
NVS-ключи прежние: `p%d` (запись), `c%d` (входящий счётчик), `n` (кол-во); новые: `r%d`
(tx-счётчик к реле).

## 5. Прошивка реле `firmware/esp32-relay`

Новый ESP-IDF-проект (target `esp32`), NimBLE-хост, одно соединение.

### 5.1 Состав

```
firmware/esp32-relay/
  CMakeLists.txt
  sdkconfig.defaults        # NimBLE, BT_NIMBLE_MAX_CONNECTIONS=1, лог UART 115200
  main/
    Kconfig.projbuild       # см. §5.2
    main.c                  # init, probe-режим, factory reset по кнопке
    relay_store.c/.h        # NVS: id, key, paired, tx/rx counters, last mask
    relay_crypt.c/.h        # seal/unseal 0x30/0x31 (те же примитивы, что в ble_phone.c)
    relay_ble.c/.h          # скан → connect → MTU → CCCD → PAIR 0x11 → обмен
    relay_logic.c/.h        # маска, импульсы, восстановление, keepalive
    host_test/              # план: векторы seal/unseal против PhoneBleCodec.kt (§5.6)
```

### 5.2 Kconfig

- `CONFIG_RELAY_GPIO` — пин реле; по умолчанию -1 = probe-режим (см. §5.7); безопасные
  кандидаты: 4, 13, 14, 25, 26, 27, 32, 33; **стрэппинг-пины 0, 2, 5, 12, 15 исключены**.
- `CONFIG_RELAY_ACTIVE_HIGH` (y) — активный уровень.
- `CONFIG_RELAY_BTN_GPIO` — кнопка на плате (если распаяна; -1 = нет). Удержание ≥ 5 с —
  factory reset: стирание id/key/счётчиков/маски из NVS, reboot.
- `CONFIG_RELAY_NAME` — имя по умолчанию «Relay-XX».
- `CONFIG_RELAY_PULSE_MS` — 300, диапазон 30–65535 (умолчание, если в 0x30 пришёл 0 — но
  0 трактуется как «держать», поэтому Kconfig-значение используется только для кнопки на плате).
- `CONFIG_RELAY_KEEPALIVE_S` — 12.
- `CONFIG_RELAY_REBOOT_MARGIN` — 4096.

### 5.3 relay_store

NVS namespace `relay`: `id` (4), `key` (16), `paired` (u8), `tx` (u32, с margin при загрузке),
`rx` (u32, запись с троттлингом 10 с), `mask` (u8 — последнее состояние, для restore).
Генерация id/key при первой загрузке из `esp_random()`.

### 5.4 relay_crypt

Тот же формат, что §3.2: `seal(key, 0x31, id, counter, body)` и
`unseal(key, pkt) → (0x30, counter, body)`. Реализация mbedtls как в компаньоне
(AES-ECB mask, AES-CTR, HMAC-SHA256/4). Тест-векторы — §5.6.

### 5.5 relay_ble

1. Скан: фильтр — имя «TBox» ИЛИ complete UUID16 `0x7B0E`; не подключаться к чужим.
2. Connect → `ble_gattc_exchange_mtu` (запрос 64).
3. Discover сервиса `0x7B0E`, характеристик `0x7B0F` (write) и `0x7B10` (notify).
4. Write CCCD 0x0001 на `0x7B10`.
5. Если `paired == 0`: писать PAIR `0x11` в `0x7B0F` раз в ~1 с (окно обучения компаньона
   ограничено 60–120 с); успех = пришёл первый 0x30 или запись сохранилась после подтверждения
   — реле не получает явного ack, поэтому `paired` ставится после сохранения NVS в момент,
   когда компаньон начал слать 0x30 (первый 0x30 валиден → paired=1). До этого окно PAIR живёт,
   повторы безвредны (pending-dedup на компаньоне).
6. Приём 0x30: unseal, проверка counter, relay_logic → ответ 0x31 с gen-эхом.
7. Keepalive 0x31 каждые `RELAY_KEEPALIVE_S` ± 2 с.
8. Разрыв: backoff 3–10 с (рандом), рестарт скана. Белый список: после сопряжения
   подключаться только к компаньону своей записи id (проверка в PAIR-фазе не нужна —
   компаньон сам отбрасывает чужие id, но реле держит адрес компаньона после первого
   сопряжения и предпочитает его).

### 5.6 Тест-векторы

`shared/.../phoneble/PhoneBleCodec.kt` — эталон. План: зафиксировать 3 вектора
(seal 0x31, unseal 0x30, отказ по tag/counter) и проверить их host-тестом на PC
(та же таблица в mbedtls на ESP32) — реле и компаньон обязаны читать пакеты друг друга
побайтово одинаково с уже работающей телефонной криптографией.

### 5.7 Probe-режим (поиск GPIO реле)

`CONFIG_RELAY_GPIO=-1` (или пункт в menuconfig): при загрузке прошивка по очереди
переключает кандидаты 4, 13, 14, 25, 26, 27, 32, 33 — каждый держит 2 с в активном
уровне и печатает в UART: `PROBE gpio=N on` / `off`. Слышно щелчок реле — пин найден,
он фиксируется как `CONFIG_RELAY_GPIO`. Probe не трогает стрэппинг-пины.

## 7. Ограничения и риски

- Слоты `BLE_DEVICE_MAX = 20` общие с телефонами и BLE-кнопками; 2–3 реле — не проблема,
  но при заполнении `ble_phone_slots_full` сработает как раньше.
- bleStatus-буферы (`phones_json` 2048 + общий `buf` 3400) — `relayDevs` для ≤ 3 реле
  укладывается с запасом; при росте числа плат пересмотреть размер.
- Реле — единственный GATT-клиент на компаньоне с неизвестным MTU-поведением стека ESP32
  (классика): запрос 64 стандартный, гейт 27 обязателен.
- «Реле молчит» без 0x30: keepalive обязателен, иначе 20-секундный idle-drop.
- Телефонное приложение, подключившись одновременно с реле, увидит только свои типы —
  расширение типов для него незаметно.
- Безопасность: PAIR открыт (как у телефона), но пишется только в окно обучения с ГУ;
  ключи 16 случайных байтов, пакеты запечатаны AES+HMAC. Устройство на расстоянии
  BLE-радиуса без ключа управление не получает.
