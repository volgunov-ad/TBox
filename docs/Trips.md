# Поездки: как это работает (простыми словами)

Ниже описано, как устроены **автоматические поездки** в приложении, в актуальной логике (версия **0.16.2**).

## Что такое поездка

Поездка — это запись с началом, (обычно) концом, пробегом и тремя независимыми типами времени:

- **время в движении** (`moving`) — двигатель работает, скорость > 0;
- **время в простоях** (`idle`) — двигатель работает, скорость = 0;
- **время парковки** (`parking`) — двигатель выключен, RPM = 0.

Дополнительно в интерфейсе и экспорте есть **«Время работы двигателя»** = `moving + idle` (без парковки).

Запись живёт в памяти и периодически сохраняется в хранилище. Хранится не более **31** последней поездки; избранных — не более **25**.

Параметр **«минут разделения поездок»** (`splitTripTime`) по умолчанию **5** минут (диапазон 1…100 000 в настройках).

## Суточная поездка

Отдельная **живая** запись с флагами `isPersistent` / `originPersistent`:

- всегда первая в списке на вкладке «Поездки»;
- не удаляется; можно переименовать;
- **никогда** не закрывается по `splitTripTime` и не становится «текущей» при resume;
- накапливает те же ездовые метрики, что и текущая (зеркалирование дельт в том же 1 с тике `onTripPeriodicSample`), а при `RPM = 0` непрерывно копит `parking` (включая ночь и gap после рестарта службы);
- виджеты поездки (`activeTripWidget*`) имеют переключатель источника: текущая (по умолчанию) / суточная; layout строк общий;
- **Сбросить**: архивирует сегмент (`endTime`, `originPersistent` остаётся) в общую ротацию до 31 обычных поездок и создаёт новую живую суточную; архив **не** участвует в resume / pending-split / `latestFinishedTrip` для виджета текущей.

Живая суточная не входит в лимит 31 и не попадает в `TripRepository.activeTrip`.

## Когда поездка **начинается**

- Двигатель завели (RPM стало > 0), активной поездки нет, и есть корректный переход через ноль RPM — создаётся **новая** поездка.
- Если при первом запуске службы двигатель уже работает и в хранилище нет активной поездки — поездка тоже может стартовать.
- Если в хранилище уже есть **активная** поездка (служба перезапустилась в процессе) — она продолжается сразу.

## Когда поездка **заканчивается** (автоматически)

- Переход RPM: **было > 0, стало 0** — поездка закрывается (фиксируется `endTime`).
- Далее действует **интервал разделения поездок** (`splitTripTime`, N минут).

## Короткая остановка (в пределах `splitTripTime`)

- Если двигатель снова запустили раньше, чем прошло N минут, продолжается **та же** поездка.
- Время между `RPM -> 0` и следующим `RPM > 0` добавляется в **время парковки**.
- Если за паузу перезапустилась только служба/ГУ, а поездка в файле уже **завершена**, она **не** открывается снова до первого **RPM > 0** (см. ниже).

## Длинная стоянка (дольше `splitTripTime`)

- Если прошло больше N минут, следующая поездка при запуске двигателя будет **новой**.
- Накопленное за длинную паузу «парковочное» время никуда не переносится:
  - не добавляется в старую поездку;
  - новая начинается с нуля.

## Перезапуск службы и продолжение недавней поездки

При старте фоновой службы:

1. **Активная** поездка из хранилища сразу продолжается (`tryResumeLastTripAfterServiceStart`).
2. **Недавно завершённая** (в пределах `splitTripTime`) **не** становится активной в JSON: в RAM запоминается `tripPendingSplitTripId`.
3. При первом **RPM > 0** служба решает, объединять ли с той записью (снимает `endTime`, добавляет parking за паузу) или начать новую поездку.

Так долгая стоянка на парковке не «приклеивается» к старому выезду только из‑за перезагрузки ГУ без запуска двигателя. Отдельного отката `endTime` при выключении ГУ без RPM в коде **нет** — опора на pending-id и первый запуск мотора.

## Как считаются времена внутри поездки

Пока поездка активна и RPM > 0:

- скорость > 0 → добавляется `moving`;
- скорость = 0 → добавляется `idle`.

Пока RPM = 0:

- `moving` и `idle` не растут;
- соответствующие паузы учитываются как `parking` только при продолжении той же поездки (окно split).

## Учёт топлива и связь с активной поездкой

- Расход и автоматические **заправки** считаются только пока поездка **активна** (`BackgroundService.applyActiveTripFuelStep`).
- Пороги в `TripFuelAccounting`: заправка — рост калиброванных литров ≥ **4%** бака за шаг; шум расхода — падение менее **0,3%** бака.
- **Отфильтрованный** процент и **калиброванные литры** обновляются **только при активной поездке** (`FuelLevelStableApply`, dwell **15 с** одного %). Источник сырого % — TBox и/или mbCAN/VHAL через `VehicleTelemetryBridge` (приоритет HU; freshness **45 с**). Bridge раз в **15 с** пишет DEBUG `TripFuel` со снимком источника (HU/TBox) и текущих значений CDR (через `TboxRepository`, без флага диагностики CAN). Температура ОЖ в поездках: на Android 9 — **только TBox** (mbCAN даёт `0.0`); на Android 10 — TBox first, HU при stale TBox.
- Жизненный цикл текущей поездки пишет DEBUG с тегом `Trip`: `start` / `resume` / `continue` / `end` / `pending_seed` / `pending_expired` (и связанные `pending_drop`).
- Сырой `fuelLevelPercentage` обновляется с шины независимо от поездки.
- При остановке двигателя последний filtered % и калиброванные литры сохраняются; при старте службы подставляются до CAN.
- Подробности — [fuel-refuels-calibration.md](fuel-refuels-calibration.md).

## Формулы метрик

- **Общее время** = `moving + idle + parking`.
- **Время работы двигателя** = `moving + idle`.
- **Средняя скорость без простоев** = `distance / moving`.
- **Средняя скорость поездки** = `distance / (moving + idle)` (парковка исключена).
- **Расход топлива (л/100км)** = `fuel_used * 100 / distance` (если distance > 0).

## Где что отображается

- **Вкладка «Поездки»**: moving, idle, parking, total, время работы двигателя, скорости, расход и др.
- **Экспорт поездок**: те же поля, включая парковку и расход.
- **Виджет «Текущая поездка» (полный)**: полный набор, включая парковку; **двойной тап** — завершить активную поездку.
- **Виджет (упрощённый)**: набор полей из настроек layout (парковку можно не показывать).
- **Виджет (настраиваемый)**: произвольный порядок полей (в т.ч. заправки, стоимость) — настройка на вкладке «Поездки».
- **Виджет (мини)**: **пробег**, **время в пути** (`moving + idle`, не общее с парковкой), **л/100 км**, **израсходовано л**.

## Обратная совместимость

- У старых поездок `parkingTime` в JSON может отсутствовать → читается как `0`.
- Миграция старых данных не выполняется.

## Ручное «Завершить поездку»

- Кнопка на вкладке «Поездки» или двойной тап по полному виджету.
- Текущая поездка закрывается; сразу создаётся новая (с учётом текущего RPM и базы топлива).

## Импорт/перезагрузка и резервная копия

- Импорт JSON: данные из файла — источник истины; авто-resume недавней завершённой поездки **не** запускается.
- **Экспорт JSON**: если в момент экспорта есть активная поездка, в **файле** она записывается как завершённая (время экспорта); работающая поездка в приложении **не** закрывается.

## Краевые случаи

- Часы ГУ ушли назад (`now < endTime`) — недавнюю завершённую поездку не продолжают.
- Ложные RPM по CAN могут влиять на авторазделение.
- Старые поездки вытесняются при превышении лимита **31**.
